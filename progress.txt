US-LEG001 — Account deletion no longer throws for members who joined via invite
================================================================================
Status: PASS

Problem: invite_tokens.used_by was declared inline as `used_by UUID REFERENCES
  users(id)` (00001_create_core_tables.sql:163) with no ON DELETE clause, so it
  defaulted to NO ACTION. It is the ONLY user-referencing FK in the schema
  without an explicit ON DELETE rule (re-verified with a multiline-aware scan of
  every migration). delete_user_account() therefore raised a foreign-key
  violation on `DELETE FROM users` for anyone who had redeemed an invite —
  i.e. essentially every invited Receiver and Viewer. Owners usually escaped it
  because `DELETE FROM families WHERE owner_id = ...` runs first and cascades the
  family's tokens away. User-visible symptom: type DELETE to confirm, tap Delete
  Everything, receive the generic error alert (SettingsView.swift:315). That made
  the erasure right advertised at Privacy.tsx:289 and Terms.tsx:286 unusable
  (GDPR Art. 17 / CCPA 1798.105).

Fix: supabase/migrations/00050_invite_tokens_used_by_on_delete.sql — drops the FK
  by pg_constraint catalog lookup (not by assuming the default name) and re-adds
  it with ON DELETE SET NULL. SET NULL not CASCADE: used_by is an audit
  breadcrumb on a token belonging to someone else's family, so erasing the
  departing user should clear the reference rather than delete the owner's row.

Backward-compat (CLAUDE.md section A): additive and forward-only. No column
  renamed, no table dropped, no type changed, no RPC signature touched, no
  on-the-wire JSON shape changed. used_by was already nullable and unredeemed
  invites already carry NULL there, so no client can be surprised by the value.

Verification: run against a real PostgreSQL 16.13 cluster rather than by
  inspection. Rebuilt the users/families/family_members/invite_tokens subset
  verbatim from 00001, seeded an owner plus a receiver holding a redeemed token,
  then ran the delete_user_account delete sequence for the receiver.
    BEFORE — ERROR: violates foreign key constraint "invite_tokens_used_by_fkey";
             ROLLBACK; user still present. Reproduces the bug and confirms the
             auto-generated constraint name.
    AFTER  — DELETE 1; COMMIT; used_by nulled; owner's token row and user row
             both intact.
    RE-RUN — migration reapplied cleanly (idempotent).
  The migration's own verification block RAISEs an exception unless confdeltype
  is 'n', so a future environment that drifts will fail loudly at migrate time.

Deploy note: this migration only runs from main via supabase-migrations.yml with
  production environment approval and a pre-migration backup, per CLAUDE.md. No

US-IOS139 — Don't finish a StoreKit transaction whose sync failed      2026-09-09
================================================================================
Both call sites already knew the rule and said so in comments:

  "Transaction.updates only redelivers *unfinished* transactions, so finishing
   first means a renewal whose sync fails is never re-pushed — the user silently
   loses provisioned entitlements."

And then both finished unconditionally, because syncSubscriptionToBackend
returned Void and swallowed its own failure after three retries. There was no
way for a caller to know. The code did exactly what its own comment said must
not happen.

  mod  ios/DailyOK/Services/SubscriptionService.swift
  mod  ios/DailyOK/App/DailyOKApp.swift
  mod  ios/DailyOKTests/SubscriptionServiceTests.swift   + 4 tests

The sync now returns SyncOutcome: .synced, .transientFailure, or
.permanentlyRejected. Only .transientFailure holds the transaction open. The
permanent case is finished deliberately — a deterministic 4xx will not succeed
on the tenth launch either, and holding it would mean StoreKit redelivering it
forever. That is the same dead-letter reasoning as the offline check-in queue in
US-IOS099, using the NetworkRetry.isNonRetryable classifier that already exists
for it.

The second half was worse, and quieter. reconcileEntitlementsToBackendOnce set
its once-per-launch latch BEFORE doing the work:

    guard !hasReconciledThisLaunch else { return }
    hasReconciledThisLaunch = true        // burned whether or not it worked
    await reconcileEntitlementsToBackend()

It runs at startup, which is exactly when the network is least likely to be up.
One failed attempt disabled reconciliation for the whole process lifetime. Pair
that with a purchase whose sync had also failed and the user stays un-provisioned
until they think to force-quit and relaunch. The latch now closes only on
success, and a connectivity-restored observer retries — the same pattern
HeartbeatService already uses for the same reason (US-IOS136).

The message shown after a failed sync said "It will retry automatically." In
session, nothing did. It now says setup is still finishing and will retry
shortly, which is true, and the permanent-rejection case says to contact support
instead of implying a retry that will never help.

The decision is a pure value, so the tests cover it without StoreKit. One of
them asserts that exactly ONE outcome holds a transaction open — a future case
added without deciding this is either a paid subscription silently lost or a
redelivery loop, and neither should be reachable by forgetting.

NOT compile-verified: no macOS or Xcode here. Reviewed by reading.
Deliberately not done: removing the new observer in deinit. SubscriptionService
is a singleton that never deallocates, and touching MainActor properties in
deinit is a compile risk I cannot check from here.

US-IOS145 — Refresh the mirrored token before confirming delivery     2026-09-09

It usually had. Supabase access tokens last about an hour. This app's entire

FOUND: a late offline sync fabricates a check-in for TODAY.

OfflineCheckInService.syncPendingCheckIns replays every queued row through
`process-checkin-response`. That request carries no client timestamp, and the

Server: `occurred_at` is an optional RFC 3339 request field. resolveOccurredAt
validates it — 7-day max age, 5-minute future skew, clamps a small future value
to now — and NEVER rejects the request: refusing a check-in is itself an
escalation, so a malformed value from a future client degrades to now(), which
is exactly today's behaviour. checked_in_at is written from it, and both the
local-day and the slot_key dedup key off it.

Backfill semantics, which is the part that matters. A check-in whose local day
is already over repairs history; it must not speak for today. So it does NOT
clear a pending checkin_request and does NOT end a running escalation Live
Activity — otherwise a three-day-old queued tap would silently stand down a live
escalation, which is the same false reassurance in a new place. Any push it
sends carries the weekday and date ("Late check-in ✓ — Mon, Mar 9, 10:03 AM.
Their phone was offline… this does not cover today"), because a bare time on a
notification received Thursday reads as Thursday. A late-delivered help request
keeps its urgency; it just says when.

`backfilled` added to the response. Additive — Swift Decodable and the Android
adapters ignore unknown keys — per the CLAUDE.md API rules.

FOUND WHILE IN HERE — a live DST bug, not part of the story:

localDayBoundsUTC computed local midnight using the UTC offset in effect at the
instant passed in. On a DST transition day that is not the offset that was in
effect at midnight, so the entire day window slid an hour: on the US
spring-forward Sunday it ran 23:00 the previous local day → 23:00 that day. A
check-in made at 23:30 local on that Sunday fell OUTSIDE its own day, so the
server's dedup and the app's Calendar.current.startOfDay disagreed — the exact
permanent-Pending failure the function's own comment says it exists to prevent.
Twice a year, for everyone.

Now resolved in two passes (offset at the candidate midnight, not at midday) and
the end bound is the next local midnight rather than start + 86,400,000ms.
Verified: spring-forward day 23h, fall-back day 25h, ordinary day 24h, and a
timezone ahead of UTC.

live check-in still omits it, so that request is byte-identical to what shipped

test. The two bounds have to agree: past the server's bound it falls back to

first time the library changed them — and it does change: v3 moves the default
service to the host bundle identifier. Owning the storage makes the purge
version-independent.

SupabaseSessionStorage writes under KeychainService.serviceName, so the existing
deleteAll() — which deletes by service rather than by an enumerated key list —
already sweeps the session up, and a key added later needs no coordination.
Accessibility AfterFirstUnlockThisDeviceOnly, matching SharedKeychain: out of
encrypted backups, still readable during background work on a locked device.

The migration is the part that matters for shipping. retrieve() falls back to
the SDK's old service once per key and moves the item across, so this does NOT
sign out every existing user on update — the read-old-write-new shim CLAUDE.md
requires for on-device state. remove() clears both copies so a sign-out cannot
be resurrected by the shim, and purgeIfFreshInstall now also calls
purgeLegacySDKItems() so the shim cannot adopt the previous owner's session on a
fresh install.

The new files are registered in project.pbxproj in all four places (build file,
file reference, group children, sources phase) — this project has no
file-system-synchronized groups, so a file not registered simply does not
compile.

NOT DONE, and stated rather than glossed:
  - AC4, verifying install → sign in → delete → reinstall on a real device or
    simulator. No macOS/Xcode here. The change is reviewed by reading and by the
    SDK source; it wants a real run before release.
  - AC5, Package.resolved. Filed as US-IOS148 instead of attempted: a correct

FOUND: the watch threw away check-ins it had already told the receiver were sent.

WatchOfflineQueue was a single slot holding one marker, valid only for "today".
The reasoning behind one-per-day was right — the server dedupes per local day —
but the edges lost real check-ins:

  - A tap at 23:55 with no network queues a marker. If it has not flushed by
    midnight, `hasPending` reads it as stale and CLEARS it. The watch had
    already played the success haptic and shown "all set". The check-in is gone,
    nobody is told, and the owner escalates on a day the receiver answered.
  - One slot means a tap on a new day, while the previous day's is still
    pending, has nowhere to go: `enqueue` sees `hasPending` and returns.

Both are now fixable rather than merely detectable, because the server accepts
`occurred_at` as of iteration 2. Before that there was nowhere to put "when".

CHANGED:
  new  ios/DailyOK/Shared/OfflineCheckInMarker.swift        (marker + pure policy)
  new  ios/DailyOKTests/OfflineMarkerPolicyTests.swift      (13 tests)
  mod  ios/DailyOKWatch/WatchOfflineQueue.swift             (rewritten)
  mod  ios/DailyOKWatch/WatchCheckInModel.swift
  mod  ios/DailyOK/Shared/SharedCheckInClient.swift
  mod  ios/DailyOK.xcodeproj/project.pbxproj

One marker per local day, each stamped with the moment it was made, flushed
oldest-first with that moment as `occurred_at`. A repeat tap on a day already
queued still collapses — and keeps the FIRST timestamp, which is when the
receiver actually answered — while an urgent tap still upgrades the day's type
and a plain OK never downgrades it (US-IOS119 preserved).

Three consequences that had to be handled, each of which would otherwise have
reintroduced the false "they're fine" from the other direction:

  - SharedCheckInClient no longer flips `hasCheckedInToday` when it is flushing
    an earlier day. That flag drives the watch face and the widget, so setting
    it for a backfill would put "all set" on a glanceable surface for a day
    nobody has answered.
  - A successful live check-in now clears only TODAY's marker, not the queue. It
    settles today; it says nothing about a previous day's tap still waiting.
  - The "queued" indicator asks `hasPendingForToday`, not `hasPending` — a
    marker from yesterday is real and will be sent, but it does not mean today
    is done.

The decisions live in a pure `OfflineMarkerPolicy` in Shared/ (app + watch
targets) rather than inside the queue, because the storage is App Group

what makes the 13 tests possible; they cover the 23:55 rollover, the new-day
tap, per-day collapse, urgency upgrade and non-downgrade, the replay window in
both directions, a future-dated marker from a wrong clock, ordering, the real
bound (one/day × 7 days = 8, not the nominal cap), and what a glanceable surface
should show.

The replay window is asserted equal to OfflineCheckInService.maxReplayAge, so
the phone, the watch, Android and the edge function now all agree by test rather
than by comment.

Migration: the old single-slot keys are read once on first access, folded into
the new array, then removed — an upgrade must not drop a check-in already
waiting on someone's wrist. Done on read rather than at launch because the
notification controller queues from a background wake that runs no launch code.
